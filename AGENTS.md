# AGENTS.md: working agreement for any AI coding agent on this repository

Project: Sawdagar Dokanpat, a multi-vendor marketplace for Bangladesh (portfolio project, deployed free on Vercel).
Repository: https://github.com/ibrahimSumon47/sawdagar-dokanpart (public). Only branch: `main`.

## 1. Reading order at the start of EVERY session (do not skip)
1. `AGENTS.md` (this file)
2. `docs/PROJECT_STATE.md` (what is done, in progress, next, blocked)
3. `docs/LESSONS.md` (mistakes already made; never repeat them)
4. `docs/REQUIREMENTS_LOG.md` (everything the owner has asked for, newest last)
5. The `docs/spec/*` file(s) relevant to the current phase
If sources conflict, priority is: newest owner instruction in REQUIREMENTS_LOG > docs/spec > this file > your own assumptions. If something is unclear and reversible, decide, then record the decision in `docs/DECISIONS.md`. Ask the owner only when blocked on something irreversible or when a secret/account action is needed.

## 2. Git rules (hard rules, no exceptions)
- Use ONLY the `main` branch. Never create branches, forks, tags (unless the owner asks), or pull requests.
- Commit identity: use whatever `git config user.name` and `git config user.email` already return on this machine. Check them before the first commit of every session. Never change git config, never use `--author`, never add `Co-authored-by` or `Signed-off-by` trailers, never commit as a bot, tool or team identity. After each commit run `git log -1 --format='%an <%ae> | %cn <%ce>'`. If it is not the owner's identity, STOP, do not push, and tell the owner.
- Never force-push, never rewrite or amend commits that were already pushed.
- Commit after every finished slice (small, logical, one concern per commit), then immediately `git push origin main`.
- Commit messages: Conventional Commits, imperative, specific, at most 72 characters in the subject, no emojis, no tool names, no "generated by" text. Good: `feat(cart): group drawer items by vendor`. Bad: `update files`.
- First-time setup only if the folder is not yet a git repo: `git init`, `git branch -M main`, `git remote add origin https://github.com/ibrahimSumon47/sawdagar-dokanpart.git`, commit with a real message (for example `chore: initialize repository`), `git push -u origin main`. If a remote already has commits, run `git pull --rebase origin main` first.
- Never commit: secrets, `.env*` (except `.env.example`), `node_modules`, build output, logs, files over 1 MB (except images in `docs/screenshots`).

## 3. Free-only policy
- Every service must be free forever, with no credit card and no time-limited trial, and must not add watermarks or expire. Before adopting any service or package, check its current free terms and license. Record the result in `docs/adr/ADR-001-free-services.md`.
- If a limit could be hit, design around it (cache, paginate, batch, degrade gracefully with a friendly message). Never silently depend on a paid feature.
- Vercel Hobby is non-commercial: this is a portfolio store, not a shop that takes money. No real payments, ads or affiliate links. Test-mode payments are disclosed in exactly two places, nowhere else: one footer line, "Payments run in test mode. No real money is charged.", and a small "Test-mode payment" label beside the payment method at checkout. `README.md`, `/about/project` and `llms.txt` may say plainly that this is a portfolio project with seeded data; the storefront and the rest of the documentation should read as a real store.

## 4. Environment policy (no localhost)
- Do NOT start dev servers and never put localhost URLs in code, config or docs.
- Allowed locally: install, lint, typecheck, unit tests, `build`. Everything else (database migrations, seeding, end-to-end tests, Lighthouse, deployment) runs in GitHub Actions or on Vercel.
- Secrets live only in the Vercel and GitHub dashboards. Never ask the owner to paste a secret into chat. Instead, list the variable names the owner must add in `docs/DEPLOYMENT.md` under "Owner actions".
- Tooling must work on Windows, macOS and Linux: automation scripts are Node `.mjs`, use `path` helpers, no bash-only syntax.
- One exception covers a localhost service: the agentmemory daemon, which runs on the developer's own machine only. It is allowed because it is free, local and account-free, it never appears in application code, config or deployment, and the repository's own `docs/` memory files stay the source of truth. Nothing else may listen on or reference a local address.

## 4a. Global tooling
- Agent skills and reference repositories live outside this project, in `~/.agents/`, and are installed by the two-tier method in [docs/spec/06-revision-1.md](docs/spec/06-revision-1.md) section 9: clone references read-only, then install only the few skills this project uses.
- [docs/TOOLING.md](docs/TOOLING.md) records every tool with its version, install location and the reason any tool was skipped. It also carries a "Reproduce on your machine" section. Update it in the same commit that installs or skips a tool.
- Never load a whole skill library into a session and never copy third-party code, assets or text into this repository.

## 5. Work protocol (the slice loop)
1. Read the reading-order files. State in `docs/PROJECT_STATE.md` under "Now" exactly what slice you are doing.
2. Implement ONE vertical slice (UI + API + database + tests + docs for one capability). Keep changes focused.
3. Run `pnpm lint && pnpm typecheck && pnpm test && pnpm build`. Fix everything before continuing.
4. Update docs (see Definition of Done), update `docs/PROJECT_STATE.md`, append `CHANGELOG.md`.
5. Commit and push. Check the Vercel deployment and the GitHub Actions run. If either fails, fix it first.
6. Move to the next slice. Do not start a new phase until the current phase's acceptance criteria in `docs/spec/05-roadmap.md` are met.

## 6. Definition of done for every slice
- Works at 360, 640, 768, 1024, 1280 and 1536 px; light AND dark theme; English AND Bangla strings (once i18n exists).
- Has a loading skeleton that matches the real layout (see design spec), an empty state, and an error state.
- Keyboard accessible, correct ARIA, visible focus, color contrast at WCAG 2.2 AA.
- Input validated on the server with Zod. Authorization enforced on the server.
- Tests exist for the business logic and the main user path; all pass.
- Docs updated: `docs/FEATURES.md` (feature to file paths), `docs/API.md` or OpenAPI if endpoints changed, `docs/DATABASE.md` if the schema changed, ADR if a significant decision was made.
- No TODO comments, placeholder text, lorem ipsum, `console.log`, commented-out code or unused files.

## 7. Code standards
- TypeScript strict. No `any` (use `unknown` and narrow). No non-null assertions without a reason.
- One responsibility per file, clear names, consistent folder structure. Domain logic lives in `packages/domain`, never inside UI components or controllers. Component size rules are in section 11.
- Reuse before writing: search for an existing component, hook or helper first. Never duplicate logic. Shared code goes in `packages/*`.
- Comments: TSDoc on every exported function, class and type. Inline comments explain WHY, or a non-obvious step. Algorithm and CS-core modules get thorough step-by-step comments because they exist to show understanding. Do not comment obvious code.
- Errors: typed errors, never swallow exceptions, user-friendly messages, error codes in API responses.
- Dependencies: add a package only if needed; check license, maintenance and bundle size; pin versions in `docs/TECH_VERSIONS.md`.

## 8. Craft and authenticity bar
The repository must read like a carefully engineered product by one consistent developer:
- Delete framework boilerplate (default Next.js page, starter CSS, unused assets).
- One consistent visual language, driven by design tokens, not ad-hoc values.
- Real, believable content in the UI and seed data. Natural wording: avoid marketing filler like "seamless", "leverage", "elevate", "cutting-edge", "robust", "unlock".
- Commit history looks like normal incremental development: small commits, logical order, natural messages.
- README and docs are honest: include a "Known limitations" section and state clearly that payments are sandbox and data is demo data.

## 9. Memory files you must maintain
- `docs/PROJECT_STATE.md`: sections Done / Now / Next / Blocked / Known issues. Update after every slice.
- `docs/REQUIREMENTS_LOG.md`: whenever the owner gives a new instruction or changes something, append it with date, the instruction in the owner's words, and status (todo / done / dropped).
- `docs/LESSONS.md`: whenever the owner corrects you or a check fails because of your mistake, append: what went wrong, the rule to follow next time. Read it every session.
- `docs/DECISIONS.md` plus `docs/adr/`: every non-trivial choice, with alternatives and reasons.

## 10. Never do
Never use paid or trial services. Never create other branches or add co-authors. Never force-push. Never commit secrets. Never run dev servers. Never use localhost. Never leave placeholder content. Never skip skeletons, empty states or error states. Never trust client-sent prices or roles. Never mock inside production code paths (demo adapters must be explicitly named and flagged). Never mark a task done without running the checks.

## 11. Component rules (the owner must be able to read and understand every file)
- Build everything as small components. One component, one job. Aim for under 80 lines per component and never above 150; if a component grows, split it. Page files (`page.tsx`) stay thin (under 60 lines): they only compose components and fetch data.
- Make a component for every repeatable or meaningful piece of UI: buttons, price tag, rating stars, product card, vendor badge, quantity stepper, cart row, address form field, stat tile, table row, empty state, and so on. Do not copy markup between files.
- Every component lives in its own folder with a clear name: `ComponentName.tsx`, `ComponentNameSkeleton.tsx` (when it loads data), `index.ts`, and a test or story when it has logic. Shared components go in `packages/ui`; feature-specific ones go in `apps/web/features/<feature>/components`.
- Props are typed with a named interface, and each component starts with a short TSDoc block: what it is for, where it is used, and what each prop means, in plain language.
- Logic goes in hooks and utility functions with descriptive names, not inline in JSX. Backend code follows the same idea: small services, one responsibility per file.
- Maintain `docs/COMPONENTS.md`: an index of every component with a one-line purpose, its props and its file path. Update it in the same commit that adds or changes a component.
- Files over 150 lines (other than generated files, seed data and the CS-core algorithm modules) must be split before committing.

## 12. Installing tools and packages
- If a tool or package is needed and is missing, install it yourself (npm, pnpm, winget or the platform's package manager). Do not stop to ask. Only ask the owner when an action needs administrator rights that you cannot get, an account sign-in, or a payment (never accept a payment or paid plan).
- Install only free, actively maintained software with an open license. Prefer project-local dev dependencies; install globally only for CLIs used across the project. Record every new tool and its version in `docs/TECH_VERSIONS.md`, and note in `docs/DEPLOYMENT.md` anything the owner must do manually.
- The owner uses Windows. Commands and scripts must work on Windows, macOS and Linux (Node `.mjs` scripts, no bash-only syntax).
